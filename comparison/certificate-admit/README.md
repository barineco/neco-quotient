# 証明書照合の共通の比較

このディレクトリでは、証明書の照合の結果を比べるための共通の事例を扱います。同じ事例を各言語の照合に渡し、受理と失敗が Lean の結果と一致することを確かめます。

## ファイル

| ファイル | 内容 |
|---|---|
| `cases.json` | 通信形式の九件の事例。名前、証明書、期待値、呼び出し側の来歴を持つ |
| `lean-outcomes.json` | 通信形式の各事例に Lean の照合を適用した結果 |
| `residual-set-api-cases-v1.json` | 残余集合 API の順序、重複、要素所属を検査する、リビジョンを付けた入力 |
| `residual-set-api-outcomes-v1.json` | 残余集合 API の入力に Lean の照合を適用した結果 |

## 比較事例の型

型と欄名の対応は [言語間の型対応](../../docs/reference/type-correspondence.md) に従い、通信形式の欄名は `rule_revision` のように snake_case で書かれます。

比較事例の `RuleTable` には、全ての言語でリビジョンが一意な値が使われます。表の構築時のリビジョンの重複は、五つの実装言語で `DuplicateRule` として返されます。

## 射影ダイジェストの比較範囲

事例の射影ダイジェストは、全実装で共有する比較規約 `sha256` を持ちます。二つの射影ダイジェストが一致するには、範囲の種類と比較規約の名前も揃っている必要があります。各言語の構築子と欄の対応は、[言語間の型対応](../../docs/reference/type-correspondence.md) で定めます。

## 段階の順序

照合は次の段階を順に検査し、最初に不成立となった段階を不一致として返します。

1. `decode`: 規則のリビジョンの一致と、表への登録
2. `source`: 入力の識別子とリビジョン
3. `coordinate`: 座標
4. `observations`: 観測
5. `digest`: 射影ダイジェストの列
6. `residual`: 残余集合の要素の所属

各段階では、期待値と証明書の同じ欄を比べます。`digest` の段階の比較相手は規則の再計算の列で、全欄と列の順序が揃うことが条件です。

`decode` の段階で不一致となった場合、リビジョンが異なる場合は期待値のリビジョンが表示され、表に規則があることを期待する場合は `rule in table` が表示されます。

## 失敗の欄

| 欄 | 内容 | 言語間で比べるか |
|---|---|---|
| `operation` | 照合の操作名。`admit` | 比べる |
| `stage` | 不成立となった段階 | 比べる |
| `origin` | 証明書の規則のリビジョン、入力の識別子、入力のリビジョン | 比べる |
| `expected`、`actual` | 各言語が表示する診断の文字列 | 比べない |
| `provenance` | 呼び出し側の来歴。不一致へそのまま渡す | 各言語の検査で、入力と一致することを確かめる |
| `contributing` | 下位の不一致の列。単独の不一致では空の列 | 比べない |

言語間の失敗の同一性は、操作、段階、`origin` の三つの欄で比べ、期待値と実際の値は診断に使う各言語の表示です。

各言語は、`origin` を証明書の規則のリビジョン、入力の識別子、入力のリビジョンから作ります。Lean の照合は、証明書由来の規則のリビジョン、入力の識別子、入力のリビジョンを来歴として渡し、返された来歴から origin を読む構成です。

比較で使う Lean の型と欄:

- 不一致: `Mismatch`
- 来歴: `provenance`
- 照合関数: `admitWithRules`

## 通信形式の事例

| 名前 | 変えた内容 | 結果 |
|---|---|---|
| `accepted_plain` | 通常の受理 | 受理 |
| `accepted_unicode_control` | 引用符、逆斜線、制御文字、スラッシュ、U+007F、日本語を含む証拠 | 受理 |
| `decode_version` | 証明書と期待値の規則のリビジョン | `decode` |
| `decode_unknown_rule` | リビジョンは一致するが、表に規則がない | `decode` |
| `source_identity` | 入力の識別子 | `source` |
| `coordinate` | 座標 | `coordinate` |
| `observations` | 観測 | `observations` |
| `digest` | 証明書の射影ダイジェストを再計算結果と異なる値にする | `digest` |
| `source_with_later_stages` | 入力のリビジョンに加え、座標、観測、残余、射影ダイジェストも異なる | `source` |

通信形式の事例では、入力の識別子、リビジョン、座標、観測、残余、証拠を文字列で具体化します。観測の文字列は照合の段階を独立に変えるための値であり、観測関数族の具体的な構成は [証明書](../../docs/certificate.md) が定める各型の責務です。

## 残余集合 API の事例

リビジョンを付けた二つの事例では、通信形式の正規順序とは独立に、残余集合の意味を検査します。

- `residual_order_and_duplicates`: 順序と重複だけが異なる二つの残余集合を受理する
- `residual_membership`: 要素の所属が異なる二つの残余集合を `residual` で拒否する

## 証拠の符号化とダイジェスト

比較規則は、証拠の文字列を正規 JSON の文字列として符号化し、そのバイト列の SHA-256 ダイジェストを計算します。比較事例では、次の識別子を使います。

- 規則のリビジョン: `comparison/sha256@1`
- 射影: `evidence`
- 言語間の比較規約: `sha256`

正規 JSON の文字列の規約は次のとおりです。

- 引用符は `\"`、逆斜線は `\\` と書く
- 短いエスケープで書く制御文字:
  - バックスペース: `\b`
  - フォームフィード: `\f`
  - 改行: `\n`
  - 復帰: `\r`
  - タブ: `\t`
- それ以外の U+0020 未満の制御文字は、`\u` に小文字の四桁の十六進を続けて書く
  - 例: `\u0000`、`\u001f`
- スラッシュ、U+007F、日本語は UTF-8 で書く

この規約は `neco-quotient-encoding` の文字列の書き出しの規則と同じです。Lean で事例を実行する処理も同じ規約に従い、SHA-256 はその処理の名前空間で計算されます。

## Lean の結果の再生成

Lean の結果を作り直すには、`lean` ディレクトリで次のコマンドを実行します。

```bash
lake build
lake exe certificate_compare ../comparison/certificate-admit/cases.json ../comparison/certificate-admit/lean-outcomes.json
```

Rust の結合テストは、`cases.json` と `lean-outcomes.json` を読み、照合の結果を Lean の結果と比べます。

このテストを `rust` ディレクトリで実行するコマンド:

```bash
cargo test -p neco-quotient-comparison-tests
```

各言語の検査の実行方法は、各言語の README を参照してください。

## 保証する範囲

- 九件の通信形式: 各言語が Lean と同じ受理と失敗を返すことを、有限個の事例で確かめる
- 二件の残余集合 API: 順序と重複からの独立、および要素所属の差の検出
- 一般の性質: Lean の `Certificate` と `RuleTable` のモジュールの定理。受理の条件、段階の順序、リビジョンによる規則の選択
- 各言語の対応: 照合の実装と Lean の定義の分岐の対応。一般の性質は Lean の定理が保証する
- 利用する側の責務: 再計算の規則の正しさ、期待値の正しさ、照合済みの証明書の後の適用
